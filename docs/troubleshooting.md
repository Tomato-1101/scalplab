# トラブル対応の指針（Mac / Windows 共通）

障害が出たときに **同じ穴を掘り直さない**ための記録。Mac 側で実際に踏んだものが中心。
Windows 側の AI もこれを読んでから原因を推測すること。

## 原則

- **根本原因を直す。** `try/except` で握り潰す、フラグで回避する、リトライで隠す — どれもしない。
- **「実装した」は完了ではない。** 動いている証拠（ログ行・数値・出力）を出してから報告する。
- **2〜3 回試して直らないものは、同じことを繰り返さない。** 試したことと出力をそのまま報告する。
  推測でコードをいじり続けるのが一番時間を溶かす。
- **プロセスが生きている＝正常ではない。** 下の 2026-07-28 の事故がまさにこれ。

---

## 過去に踏んだ罠

### プロセスは生きているのに API だけ死ぬ（2026-07-28）

moomoo OpenD が**起動したまま**ポートに応答しなくなり、録画が 2 日分まるごと飛んだ。
`pgrep` では生きて見えるので「起動している＝正常」と誤判定した。

- **Errno 61（ECONNREFUSED）= 未起動**、**Errno 49（EADDRNOTAVAIL）= プロセスは生きているが API 死亡**。
  この 2 つを区別する。
- 死活監視は**ポートへの実接続**で判定する。生存していてポート不達なら **kill してから再起動**する
  （`scripts/opend_guard.sh` がこの実装）。
- kabuステーションでも同じことが起こりうる。**アプリが見えている＝ API が生きている、と判断しない。**
  `--check` が通ることを毎回の起動判定にする。

### 接続できていないのに後処理が走ってデータを壊した（同上）

接続失敗時も `finally` の後処理（finalize）が動き、**空のデータで既存 parquet を上書き**していた。

- 接続できたかを示すフラグを持ち、**接続していないなら後処理をスキップする**（`record.py` の `connected`）。
- 「失敗したときに何が起きるか」を必ず書き出してから実装する。

### 先読み（look-ahead）を自分で作り込んだ（2026-08-11）

当日終値を含む指標で「当日の寄り」を判定していて、現実離れした好成績が出た。

- **異常に良い結果が出たら、まず自分を疑う。** 手法を喜ぶ前に「その時点で本当に分かる情報か」を確認する。
- 新しい戦略は **「いつ何が分かるか」を書き出してから**実装する。
- 特徴量は原則 `.shift(1)` して前日までに限定する。

### 往復コストを片道でしか引いていなかった（2026-08-10）

`net = gross - cost_bp` で片道 3bp しか引いておらず、旧手法が黒字に見えていた。往復にするとゼロだった。

- **コストは必ず往復で引く。** 前提は手数料無料枠＋指値で往復 2〜3bp。
- 手数料が 0 円でも**スプレッド（呼値 1 ティック分）は必ず払う**。呼値 ÷ 株価 が実効コスト。

### ログが 1 日 3GB 積み上がっていた（2026-08-14）

futu SDK の既定が `file_level=DEBUG` で、相場プッシュ 1 件につき 2 行書いていた（実測 818MB/時）。

- ライブラリの**既定ログレベル**を確認する。常時受信するものは特に。
- ログの自動削除（保持日数）を最初から入れる。

### Windows では `read_text()` が cp932 で日本語 YAML を読めず落ちる（2026-08-17）

Windows 初回セットアップの pytest で 10 件失敗。うち 8 件は `Path.read_text()` を
エンコーディング未指定で呼んでいる箇所（`live.py` の load_config / resolve_params、
`record.py:75`、`datafeed/universe.py:306`）が原因。Windows の既定エンコーディングは
cp932 なので、日本語コメント入りの config YAML（UTF-8）を読むと `UnicodeDecodeError` になる。

- **`scalplab.live --check` も同じ経路（live.py:120 の live.yaml 読み込み）で起動不能。**
  疎通確認はこの修正が入るまで実行できない。
- 修正は `read_text(encoding="utf-8")` に統一する（Mac では既定が UTF-8 なので顕在化しなかった）。
- 残り 2 件は `send_notification` のテストが macOS の `osascript` 前提。実装は Windows で
  `powershell` に分岐しており正しく、**テスト側が OS 分岐に未対応**。
- 修正は Mac 側セッションで設計・実施する（Windows 側は bootstrap の指示どおり報告のみ）。

### kabuステーション配布 URL の変遷（2026-08-17）

初期の手順書に記載していた `download.r20.kabu.co.jp` は **DNS 不在**（NXDOMAIN）。
現行の公式配布は `https://download.r30.kabu.co.jp/ap/kabustation/`（kabuStation_Installer.exe）。
インストーラは Authenticode 署名が
`CN=Mitsubishi UFJ eSmart Securities Co., Ltd.`・Status: Valid で公式と確認できる。
リビジョン番号（r20→r30）は今後も変わりうるので、繋がらなければ公式サイト経由で探し直す。

## kabuステーション で想定されるエラー

実機未確認のものを含む。**遭遇したらこの表に追記する。**

| 症状 | 見るべきところ |
|---|---|
| トークン取得に失敗 | アプリが起動・ログイン済みか／設定 > API 有効化後に**アプリを再起動したか**／ポート（本番 18080・検証 18081） |
| `APIPassword が未設定`（setx 済みなのに） | `setx` は**新規プロセスにしか効かない**。setx 前から生きている親プロセス（AI セッションのシェル等）から起動すると届かない。`$env:KABU_API_PASSWORD = (Get-ItemProperty HKCU:\Environment).KABU_API_PASSWORD` で値を表示せずに読み込んでから実行する（2026-08-17 実測） |
| `--check` 終了時に `[WinError 10038] ソケット以外のものに対して操作を実行しようとしました` の WARNING | 10 秒受信の終了処理で受信スレッドが閉じたソケットを読む競合と思われる。接続 OK・購読 2/2 の後に出ており**疎通結果には影響しない**（2026-08-17 実測。実害が出たら受信ループの close 順序を見る） |
| `/board` の初回リクエストが `TimeoutError: timed out`（token 取得は成功） | 2026-08-17 実測。HTTP タイムアウト 5 秒（live.py `_default_http_request`）を初回だけ超過し、**直後の再試行から安定して 200**。アプリ再起動後のコールドスタートと思われる。premarket 本番は巡回リトライで吸収されるはずだが、頻発するならタイムアウト値と初回ウォームアップを検討 |
| `register` に反映されない | Professional プランか（**通常プランでは API 不可**）／証券コードと `exchange`（1＝東証） |
| 51 銘柄目が登録できない | **`register` は 50 銘柄上限**。さらに **2026-08-19 実測で `/board` も内部で銘柄を自動登録して枠を消費する**と判明（「register 不要だから制限なし」は誤り）。51 銘柄目以降の `/board` は `status=400, Code 4002006 レジスト数エラー` になる（premarket 初回実行で 291 銘柄中 50 銘柄しか取れず、1 周あたり約 240 件のエラー） |
| 50 銘柄超を巡回したい | **`PUT /unregister/all` → 次の 50 銘柄を `/board`、のローテーションが成立する**（2026-08-19 実機テスト: 3 バッチ × 50 銘柄で OK 149/150・失敗 1 はタイムアウト 1 件のみ・unregister/all は毎回 200）。所要は約 50 秒/50 銘柄（/board 応答 ≈0.85 秒 + throttle 0.15 秒）→ **291 銘柄 6 バッチ ≈ 5 分/回転**、08:00〜08:55 で約 10 回転できる計算 |
| 接続はできるがデータが来ない | 市場時間外なら正常。立会時間（09:00-11:30 / 12:30-15:30 JST）に再確認 |
| 朝だけ繋がらない | アプリの自動ログインが効いているか。**08:00 時点で `--check` を通す**運用にする |
| 日付が変わると落ちる | **2026-08-18 実測で確定**: 前日から起動しっぱなしのアプリは翌朝 token 取得が `status=401, Code 4001007（ログイン認証エラー）` になる（アプリの見た目は正常のまま＝「生きている≠正常」の典型）。**アプリ再起動→自動ログインで復帰**を確認済み。**含意: 朝の premarket 自動実行の前に毎日アプリを再起動する仕組みが要る**（07:55 のタスクだけでは前日起動のアプリが 401 で全滅する）。起動フローへの組み込みは Mac 側で設計する |
| ps1 が日本語コメントの位置で `MissingEndCurlyBrace` 等のパースエラー | **UTF-8 BOM なしの ps1 を Windows PowerShell 5.1 が cp932 として読む**のが原因（2026-08-21 実測。ensure_kabustation.ps1 が premarket_task.cmd の `powershell` = 5.1 経由で毎回パースエラーになっていた）。**日本語を含む ps1 は必ず UTF-8 BOM 付きで保存する**（pwsh 7 は BOM なしでも読めるので手元テストでは気付けない）。Mac で新規作成した ps1 は BOM なしになりがちなので Windows 反映時に要確認 |
| タスク実行中の premarket が途中で沈黙死（traceback なし・リターンコード 3221225786） | 3221225786 = 0xC000013A（コンソールクローズ）。タスクを `LogonType Interactive` で登録しているため **cmd の黒い窓がデスクトップに見えており、その窓を閉じると収集ごと死ぬ**（2026-08-21 実測: 09:00:20 に窓が閉じられ寄り直前 5 分の focus データを喪失）。運用: 収集時間帯（07:55〜09:07）は黒い cmd 窓を閉じない。恒久対応（窓の非表示化）は Mac 側で設計する |
| 再起動した premarket が同日 parquet を上書きし、先に録れていた行が消える | `_save` が rows 全量を同じ `data/premarket/YYYY-MM-DD.parquet` に書くため、**プロセスが再起動すると空の rows から上書きされる**（2026-08-21 実測。途中保存済みの寄り前 94 行が消えかけた→手動退避・マージで復旧）。既存 parquet の読み込み or 追記型の保存への変更は Mac 側で設計する |
| アプリ起動直後の最初の 1 周だけ /board タイムアウトが多発 | 2026-08-21 実測: アプリ起動 8 分後の初回スイープ（08:47〜08:55）はタイムアウト率 4 割超（450 秒で成功 94 件）だったが、2 回目のプロセス（09:03〜）は 100 銘柄で 3 件のみ。**各銘柄の初回 /board が遅い（コールドスタート）**と思われ、2 周目以降は正常化する。07:55 開始の本来運用なら寄りまでに複数周回るので実害は小さい |

## 報告するときの形式

原因が分からないまま人間に投げるときは、以下をそのまま貼る。**推測を先に書かない。**

1. 実行したコマンド（全文）
2. 出力（全文。省略しない）
3. 直前に変更したもの（あれば）
4. 試したこととその結果

**秘密値（APIPassword 等）が出力に含まれていないかだけ確認してから貼る。**
